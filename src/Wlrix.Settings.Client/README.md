# Wlrix.Settings.Client

The C# side of `wlrix-settings-daemon`. Any wlRIX settings app should read and write config
through this, and nothing else.

## Why it exists

`Wlrix.Settings.Keyboard` used to carry its own 250-line TOML editor, its own pidfile reader and
its own `libc kill()` for the `SIGHUP`. The next settings app — mouse, displays, appearance —
would have copied all three, and each copy would have had to learn a *different* owning
process's reload story. Worse, the hand-rolled editor had a bug that cost the user their whole
`compositor.toml`: it could not find a `[keyboard]  # japanese` header, appended a second
`[keyboard]` table, and the compositor then rejected the file and fell back to built-in
defaults.

That work now happens once, in Rust, in the daemon. This library is the thin part.

## Using it

```csharp
using var client = await SettingsClient.ConnectAsync();

// The schema: type, range, choices, unit, default and prose, straight from the daemon.
// A panel renders from this rather than hardcoding wlRIX's defaults a second time.
foreach (var setting in await client.DescribeAsync("compositor"))
    Console.WriteLine($"{setting.Key}: {setting.Kind} default={setting.Default}");

// Values, and where each came from.
var values  = await client.GetAllAsync("compositor");
var sources = await client.SourcesAsync("compositor");   // user | system | default

// One call, one write per file, one signal per owner.
var result = await client.SetManyAsync(new Dictionary<string, object>
{
    ["compositor.keyboard.layout"] = "jp",
    ["compositor.keyboard.repeat_delay"] = 300L,
});
if (result.Advice is { } advice)
    Status = advice;   // "Saved. wlrix-compositor is not running; it will read this at the next start."

// Live updates, including someone editing the file in $EDITOR.
await client.WatchAsync();
client.Changed += (_, e) =>
{
    if (e.Origin == client.UniqueName) return;   // the echo of our own write
    Dispatcher.UIThread.Post(() => Apply(e.Values));
};
```

Four things are easy to get wrong, and all four are the difference between a panel that works
and one that misbehaves subtly:

**Batch, don't loop.** `SetManyAsync` with four keys is one file write and one `SIGHUP`;
four `SetAsync` calls are four of each, and the compositor recompiles its keymap every time.
The batch is also the only version that cannot be observed halfway through.

**Filter on `Origin`.** The daemon announces every change to everyone, including the app that
caused it. A panel that acts on its own echo will re-arm its debounce timer and commit again,
forever. Compare against `SettingsClient.UniqueName`; a hand-edited file arrives as `external`,
which never matches.

**Check `HasDefault`, not `Default`.** `compositor.keyboard.layout` genuinely has no default —
absent means "let libxkbcommon decide" — while `repeat_delay` defaults to 200. A `Default` of
`""` cannot tell those apart, which is why the flag is separate.

**Signals arrive on a bus thread.** Marshal to the UI thread yourself.

## Notes

`ConnectAsync` builds its own `DBusConnection` rather than taking the shared
`DBusConnection.Session`, because an autoconnect connection refuses to report its `UniqueName` —
and without that there is no way to recognize your own echo.

There is deliberately **no fallback** to editing the TOML directly when the daemon is absent.
The daemon is bus-activated, so "not on the bus" means a broken install rather than an idle
session; and a fallback would put back exactly the duplication this library removes, in an app
that has no TOML parser to do it correctly with.

The proxy in `DBusXml/com.wlrix.Settings1.xml` is generated by the daemon's own introspection
(`just introspect` in `wlrix-settings-daemon`), so the two cannot disagree about a signature.
Strip the comments when regenerating: they are the daemon's Rust prose, and a `--` in one makes
the XML unparseable — which has already happened once.

The full interface, and what the daemon guarantees about your config file, is documented in
`wlrix-settings-daemon/README.md`.
